# Журнал изменений

Одна строка на выпуск - что изменилось для того, кто им пользуется. Состав каждого выпуска лежит в его [заметках на GitHub](https://github.com/Desko77/ai-edt/releases); здесь только указатель, чтобы историю можно было просмотреть целиком за минуту.

Версия собирается из тега: `v0.2.21` даёт `0.2.21`. В дереве исходников стоит следующий выпуск снимком - на один микро выше свежего тега.

Пресеты только-чтения выключают `naparnik` в обоих режимах. Один вопрос за раз; ответ `Pending` несет `runKey`, `cancel=true` с этим ключом останавливает вопрос. `maxToolRounds` (1..30, по умолчанию 10) всегда передается положительным числом. Разрешение тяжелого вызова держится до конца фоновой работы: ответ `Pending` больше не отпускает его на мягком таймауте, билет передается записи реестра и отпускается по завершении ее будущего (успех, ошибка, отмена, вытеснение). Опрос по `runKey` идущей работы разрешения не занимает и гейт кучи не проходит; незнакомый `runKey` идет обычным путем. Вложенный тяжелый вызов под родителем, держащим разрешение, второго не берет. Инструмент другого бандла объявляет себя тяжелым свойством службы `ru.aiedt.mcp.tool.heavy`. Другой бандл вызывает инструменты плагина службой `IToolRoad` (`call`, `resume`, `cancel`) - теми же поиском, гейтами и лимитами, что внешний вызов, на потоке вызывающего; внутренний вызов пишется в историю с полем `origin`, доводы маскируются теми же ключами. Отказ внешнего тяжелого вызова по пределу и по куче - прежний `503` с тем же телом и `Retry-After`. Тяжелое разрешение берут также `config_io operation=export_configuration_to_cf` и `operation=unpack_external_binary`, `external_object_workshop operation=import_external_object`, `infobase_admin operation=create_infobase`, `sync_control operation=rebuild_dump_info` (и `infobase_admin operation=sync_control syncOperation=rebuild_dump_info`), `extension_workshop operation=check_platform_verdict`, а также `launch_debugger action=launch` и `start_client`, когда перед запуском клиента обновляется база (`updateBeforeLaunch`). Маршрут фасада разбирает операцию так же, как сам фасад: вызов в написании camelCase (`exportInfobaseObjects`, `updateDatabase`) проходит проверку кучи и предел тяжелых вызовов, а написание, которое фасад отвергает, разрешения не берет. `config_io operation=export_infobase_objects` выгружает выбранные объекты конфигурации базы (не проекта EDT) в иерархический XML Конфигуратора: верхний объект, форму или общую форму по адресу из `objects` (русские виды принимаются, существование сверяется по модели проекта, повторы сводятся, прочие дочерние виды отклоняются до запуска). Результат ставится в `outputPath` одним переносом из служебного каталога рядом с ним; каталог назначения обязан отсутствовать или быть пустым, второй вызов в тот же путь, пока идет первый, отказывается с `runKey` первого. База берется по `applicationId` или приложению проекта, перед запуском EDT отключается от базы и после возвращается, работа держит межпроцессный замок. Ответ несет `files`, `objects`, `source: "infobase"`, `infobase`, `elapsedMs`. Пресеты только-чтения выключают операцию. `infobase_admin operation=register_infobase` добавляет существующую базу в список EDT и связывает ее с проектом: файловую по `path`, серверную по `connectionString` (`Srvr=...;Ref=...`), ровно одно из двух. Адрес, который уже есть в списке, используется повторно (`reused`; проекты, с которыми запись уже связана, - `alsoAssociatedWith`); имя, которое в списке носит база с другим адресом, отклоняется до записи (`alreadyExists`); сбой связывания снимает добавленную запись (`rolledBack`), файлы базы не трогаются. `name` обязателен для серверной базы, для файловой по умолчанию - имя каталога; `makeDefault` по умолчанию true только у проекта без приложения по умолчанию. Ответ называет приложение по умолчанию (`defaultApplication`, `previousDefaultApplication`, при сбое чтения - `defaultWarning`), проекты, приложения которых прочитать не удалось (`associationCheckFailed`), и флаг запуска в режиме обычного приложения (`ordinaryApplicationFlag`). Пресет Debug and Test выключает операцию. `register_infobase` принимает `accessMode`, `userName`, `password`: учетные данные базы записываются в зашифрованное хранилище EDT в том же вызове - после записи в списке и до привязки (тот же смысл и проверки, что у `set_infobase_credentials`), поэтому база с пользователями регистрируется без интерактивного запроса доступа; сбой записи - отказ до привязки с текстом причины, добавленная запись снимается. Ответ называет записанное (`access`, `userName`, `passwordStored`, `verifiedByReadback`); пароль не появляется ни в ответе, ни в истории вызовов, ни в журнале. Текст сбоя записи учетных данных в `register_infobase` и `set_infobase_credentials` приходит с новым и прежним паролем, замененными на `***`; длинный заменяется первым. Неизвестный модуль, метод или подсистема и селектор, который не согласуется со `scope`, отклоняются с именем. ## Как это ведётся

Строка добавляется при выпуске, а не задним числом. Если строки нет, а тег есть - это упущение, и его видно сразу: список тегов и список строк должны сходиться.

Здесь нет разбора причин и замеров. Они в заметках к выпуску, и дублировать их сюда значило бы завести второй источник правды, который разойдётся с первым.
