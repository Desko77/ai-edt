# Каталог инструментов AI-EDT

[← На главную](../../README.md) · [Пресеты](#пресеты-и-видимость) · [Фасады](#ключевые-фасады) · [Обозначения](#обозначения)

Этот каталог показывает поверхность MCP-инструментов AI-EDT по группам из настроек **Window → Preferences → AI-EDT → Tools**. Он отвечает на три вопроса:

1. какой инструмент выбрать для задачи;
2. требуется ли ему запущенная EDT, отладочная сессия или информационная база;
3. может ли вызов изменить проект или данные.

> [!NOTE]
> Текст каталога написан вручную, а вот состав инструментов сверяется автоматически: `scripts/check-tool-catalog.py` сравнивает имена в этом файле с группами `ToolCategory` и роняет сборку при расхождении. Источник истины по JSON-схемам параметров остается за `tools/list` живого сервера.

## Обозначения

| Метка | Значение |
|---|---|
| **Чтение** | Не должен изменять проект или информационную базу. |
| **Изменение** | Записывает исходники, метаданные, настройки или файлы проекта. |
| **Выполнение** | Запускает EDT/1С, тесты, запросы или код в живой сессии. |
| **Опасно** | Может удалить, импортировать, перезаписать или синхронизировать данные. |
| **Смешанный** | Поведение зависит от выбранной операции или параметров вызова. |
| **Фасад** | Единая точка входа для нескольких родственных операций. |
| **Workshop** | Высокоуровневый конструктор сложного артефакта. |

Тот же класс инструмента `tools/list` публикует в `annotations` MCP: `readOnlyHint` и `idempotentHint`
у тех, кто ничего не меняет, `openWorldHint=false` у всего, что не выходит за пределы машины. Класс
читается с пресета Read-only, поэтому он совпадает с этой таблицей; фасад, гасящий записи по имени
(`git`), читающий, пока его записи выключены. Публикуются только значения, отличные от умолчаний
спецификации, - инструмент с умолчаниями члена `annotations` не несет.

Отказ, у которого известен следующий шаг, несет его готовым вызовом в `helpHint`:
`{"tool": ..., "arguments": {...}}` и рядом деталь, если она есть. Сегодня это «проект не найден»
(`project_admin operation=list_projects`, рядом `suggestedProjectName` при близком имени открытого
проекта) и «владелец не найден» в записях метаданных (`insights operation=semantic_metadata_search`
по имени объекта).

Служба кластеров не является службой OSGi и может отсутствовать - операции отвечают `serviceUnavailable`, а не падают. Пять записей гасятся пресетами Read-only, Debug & Test и Code Review каждая своей дверью и отвергаются до чтения файла. |

Пять записей гасятся пресетами Read-only, Debug & Test и Code Review каждая своей дверью и отвергаются до чтения файла меток. |
| `create_tag` | Запись (операция фасада `tag_admin`) | Имя, под которым создание метки гасится пресетами. Вызываемо и напрямую как алиас `tag_admin operation=create_tag`. |
| `update_tag` | Запись (операция фасада `tag_admin`) | Имя, под которым переименование и смена вида метки гасятся пресетами. Вызываемо и напрямую как алиас `tag_admin operation=update_tag`. |
| `delete_tag` | Запись (операция фасада `tag_admin`) | Имя, под которым удаление метки гасится пресетами; `dryRun` проходит ту же дверь. Вызываемо и напрямую как алиас `tag_admin operation=delete_tag`. |
| `assign_tag` | Запись (операция фасада `tag_admin`) | Имя, под которым назначение меток объекту гасится пресетами. Вызываемо и напрямую как алиас `tag_admin operation=assign_tag`. |
| `unassign_tag` | Запись (операция фасада `tag_admin`) | Имя, под которым снятие меток с объекта гасится пресетами. Вызываемо и напрямую как алиас `tag_admin operation=unassign_tag`. |
| `git` | Фасад · Смешанный | Git репозитория проекта внутри IDE через JGit, который среда несет сама: `status` (дерево и индекс против HEAD, ahead/behind по tracking-ветке), `branches` (текущая первой), `log` (последние коммиты, `limit` до 100), `commit` (постановка и коммит названных файлов - `paths` поименно и обязательно, add-all отвергается; автор и все пути проверяются до записи в индекс: `.`, `*`, шаблон по `*`/`?`/`[`, каталог, абсолютный путь и `..` отвергаются по имени, а удаленный отслеживаемый файл коммитится как удаление; в коммит идут только названные пути - застейдженное до вызова остается вне коммита, и вызов, у которого ни один названный путь не изменен, отвергается; ответ несет `sha`, `shortSha`, `author`, `filesCount`, `files`, `changes` (путь и вид изменения), `message` и, когда есть, `unchanged`; автор из `user.name`/`user.email` репозитория или `authorName`/`authorEmail`; в ответе `boundInfobase`, когда ветка привязана к ИБ), `checkout` (`branch`, `createBranch`; переход, который перезаписал бы незакоммиченные файлы, отвергается с их списком в `conflicting` и ничего не меняет), `show_file_changes` (построчный diff файла `filePath` между `fromRef`, по умолчанию HEAD, и `toRef`, по умолчанию рабочий каталог; без `filePath` - перечень измененных файлов со счетчиками строк и без hunk-ов (файл больше 5 МБ с любой стороны отвечается размером `sizeInBytes` с `linesNotCounted: true`, без счета строк), не больше `limit` (по умолчанию 50, не больше 200), общее число в `totalFileCount`, признак усечения `truncated`; `granularity=method` только для одного `.bsl` и называет измененные процедуры и функции, правки вне методов входят в счетчики файла), `revert_file` (один файл `filePath` из коммита `fromRef`, по умолчанию HEAD, с концами строк, которые дал бы `git checkout` этого пути по `.gitattributes` и `core.autocrlf`, без правила - концы строк текущего файла; ответ несет `lineEndings`, `bytesWritten`, `restoredFrom`, `fileStatus`, `indexUntouched`, а при `dryRun` - `bytesWritten: 0`, `restoredFrom`, `lineEndings`, `files` с diff и `note`, без `fileStatus` и `indexUntouched`; `dryRun=true` ничего не пишет и при открытом редакторе с несохраненными правками, запись в этом случае отвергается; для `.form`/`.mdo`/`.dcs` ответ советует `revalidate_objects`), `create_merge_restore_point` (файлы проекта без движения HEAD: для проекта в git - коммит под ссылкой `refs/aiedt/merge-restore/<pointId>`, иначе копия каталога проекта; `compare_three_way` с изменяющим намерением записывает точку сам до объединения и отвечает `mergeRestorePoint`, без точки объединение не начинается, `mergeStarted: false`; сбой записи индекса называет каталог хранилища и причину, созданная ссылка или копия убирается), `restore_merge_point` (`pointId`, по умолчанию последняя точка проекта; возвращает файлы точки и удаляет файлы проекта, которых в точке нет, ответ несет `restoredFiles`, `restoredCount`, `unchangedFiles` и `removedFiles` - только реально удаленные; файл, байты которого на диске уже совпадают с точкой, не переписывается и попадает в `unchangedFiles`; при частичном сбое ответ ошибки называет невосстановленные файлы в `unrestoredFiles`, несет `removedFiles`, а очистка лишних файлов и обновление рабочей области выполняются; лишний файл, который не удалось удалить, назван с причиной в `cleanupFailures`, сбой обновления рабочей области - в `refreshFailure`, и каждый из них делает ответ ошибкой, называющей его рядом с первичной причиной; база не откатывается), `delete_merge_restore_point` (`pointId` обязателен, последняя точка сама не выбирается; удаляет ссылку или копию и запись индекса точки, файлы проекта не трогает; неудаленные ссылка или каталог копии - ошибка с причиной, запись индекса сохраняется, и повторный вызов доудалит точку; точка другого проекта - отказ `No merge restore point`). Записи `commit`, `checkout`, `revert_file`, `restore_merge_point`, `create_merge_restore_point` и `delete_merge_restore_point` выключаются пресетами Read-only, Debug & Test и Code Review каждое своей дверью - `git_commit`, `git_checkout`, `git_revert_file`, `git_create_merge_restore_point`, `git_delete_merge_restore_point` - и отвергаются до постановки, возврата, записи или удаления файлов; создание точки в рабочее дерево не пишет, но заводит ссылку в репозитории либо копию каталога проекта. |

## Аналитика конфигурации

Высокоуровневый анализ структуры и последствий изменений.

| Инструмент | Режим | Назначение |
|---|---|---|
| `dependency_graph` | Чтение | Строит граф зависимостей между объектами метаданных и модулями BSL. Уровень `metadata` несет объекты метаданных, `mixed` - объекты метаданных и модули BSL. Служебный узел EDT не попадает в граф ни на одном из них и отбрасывается с обеих сторон ребра, как источник и как цель; отброшенные ребра считаются по одному разу в `internalEdgesDropped`, и на уровне `metadata` туда же идет ребро с модулем BSL. Корень, который не является объектом уровня, тоже не становится узлом - его имя идет в `internalRootsDropped`. Повторы одного `from`/`to`/`via` сливаются в одно ребро, `count` - число ссылок между этой парой (одна ссылка, встреченная обходом с двух сторон, остается одной; поле пишется, когда больше 1), `maxEdges` считает уже слитые. `edgeKinds` оставляет только названные виды `via` (строка через запятую или массив); невстреченный вид - в `unmatchedKinds`, это не отказ. ## Ключевые фасады

Фасады уменьшают размер `tools/list`: вместо набора родственных standalone-инструментов агент видит одну точку входа и выбирает действие через параметр `operation`.

У большинства фасадов встроена справка:

```json
{
  "operation": "help"
}
```

Для подробностей конкретной операции используется `topic`:

```json
{
  "operation": "help",
  "topic": "text_search"
}
```

`topic`, называющий операцию, отвечает перечнем ее доводов: имя, вид, обязательность и описание. Перечень строится из схемы того инструмента, в который операция направляется, поэтому он не расходится с тем, по чему проверяется вызов. Операция, которую фасад обрабатывает сам, а не направляет в инструмент, так и отвечает - что отдельной схемы у нее нет; тема, не называющая ни операции, ни встроенного раздела, отвергается. Три ответа различимы намеренно: «не описано» и «нет такой темы» - разные вещи.

Довод `find` ищет по справке фасада подстроку без учета регистра, включая кириллицу: `operation=help find=закладки` отвечает кусками справки, где слово встретилось. Кусок - это раздел от заголовка до следующего заголовка; в теме-операции это описание одного довода. Несколько слов через пробел должны встретиться все в одном куске. Морфологии нет, поэтому при пустом ответе ищите по основе слова. Заданный вместе с `find` довод `topic` ограничивает поиск этой одной темой. Ответ называет общее число совпадений и показывает первые десять кусков, каждый с пометкой, из какой темы он взят. Ноль совпадений - не ошибка: ответ перечисляет темы, которые можно спросить целиком.

<a id="code_search"></a>
<details>
<summary><code>code_search</code> - поиск и навигация по коду</summary>

Операции: `text_search`, `object_references`, `method_references`, `resolve_symbol`, `call_hierarchy`, `symbol_info`, `content_assist`, `outgoing_structures`, `help`.

Используйте фасад для исследования BSL и модели перед изменениями. Все операции только читают проект. Справка по операции здесь написана вручную, а не построена из схемы инструмента: фасад переименовывает все восемь операций и у пяти переписывает доводы, поэтому схема инструмента назвала бы то, что получает он, а не то, что отправляет вызывающий.

Долгий обход - поиск ссылок по проекту и аналитика по всей конфигурации - отвечает `Pending` с
`runKey`; поиск по тексту идет своим бюджетом `timeoutSeconds` и при исчерпании отвечает с пометкой
`SCAN CUT SHORT`. Отмена поднимает флаг, который обход читает, и он останавливается на ближайшей границе; пока
отмененный обход не завершился, вызов с теми же доводами второй обход не запускает и отвечает `stillStopping`.
Отмена (`tasks/cancel`) отвечает пустым объектом, а задание переходит в состояние `cancelled`: в
`statusMessage` сказано, чем кончилась остановка - работа остановлена (написанное остается записанным),
работа получила команду остановиться, но еще идет и может писать, либо сервер только перестал ее ждать,
а процесс Конфигуратора после запуска не прерывается. Ключ запуска удерживается, пока тело вызова не
завершится.

`object_references` считает найденные ссылки по фазам отдельно, до десятикратного предела на фазу, и печатает
в каждой категории не больше предела строк; раздел кода идет перед метаданными, а остаток строк назван как
"... and N more". Обрезанный ответ называет соседние проекты, которые не были открыты, `limit` не больше нуля
отвергается до начала поиска, а сбой BSL-фазы отражается как неполный ответ. Сбой индекса при сборе вызывающих
виден и в прямом, и в транзитивном графе вызовов.
</details>

<a id="launch_debugger"></a>
<details>
<summary><code>launch_debugger</code> - полный цикл отладки</summary>

Объединяет запуск/Attach, line и exception breakpoints, `run_to_line`, ожидание suspend, чтение и изменение переменных, stepping, resume, terminate, evaluation и profiling.

Большинство операций требует действующей конфигурации запуска EDT; операции с кадрами требуют приостановленного потока.

`launch` принимает `startupOption` - строку аргументов `/C` для клиента, записываемую в копию конфигурации запуска, - и `waitForEndpoint` с `endpointTimeoutSeconds`: запуск считается готовым, когда открытый им адрес отвечает (GET, итоговый статус ниже 500), а не когда процесс существует. То же у `start_client` фасада `infobase_admin`.

Клиент и режим запуска. Конфигурация, у которой основной режим запуска - обычное приложение, запускается в
толстом клиенте: `clientType` автосозданной конфигурации `thick`, у существующей клиент подменяется в копии на
время запуска, а в дополнительные параметры запуска базы записывается `/RunModeOrdinaryApplication` - на
ссылке базы, которую EDT держит в памяти на время сеанса; список баз на диске (общий с лаунчером платформы) не
пишется, потому что его запись заставляет EDT перечитать список и снять приложение с каждой конфигурации
запуска. Платформа берет последний флаг режима в командной строке, поэтому он перекрывает
`/RunModeManagedApplication`, который EDT ставит толстому клиенту. Управляемый режим убирает флаг.
`clientType` (`thin`, `thick`, `web`) и `runMode` (`ordinary`, `managed`) задают выбор явно; `clientType=thin`
на конфигурации обычного приложения без `runMode=managed` отказывает - обычные формы в тонком клиенте не
открываются. Ответ несет `clientType`, `clientTypeSource`, `runMode`, `runModeSource`, `runModeFlagState`
(`added`, `removed`, `present`, `absent`, `not applied: ...`), `runModeFlagScope` и
`infobaseAdditionalParameters`.

Запуск с обновлением базы отказывает, если база не пришла в `UPDATED`: обновление уже идет, загрузка
закончилась другим состоянием, приложение не найдено или не разрешилось. Отказ несет `databaseUpdate` и
`databaseState`, а запущенная сессия - `databaseUpdate`. Ответ `FULL_UPDATE_REQUIRED` ведет к полному
обновлению, а проверка "уже запущено" идет до обновления.

Пресет, выключивший `update_database` (Read-only, Debug & Test, Code Review), с явным
`updateBeforeLaunch=true` отказывает запуск до обновления и до запуска текстом выключенного инструмента,
называя `updateBeforeLaunch=false` как способ запустить базу как есть. Вызов без довода под таким
пресетом запускает без обновления и отвечает `databaseUpdate=SKIPPED_BY_PRESET` с пояснением
`databaseUpdateNote`; обновить базу - `infobase_admin operation=update_database` под пресетом, который
это разрешает. `start_client` (умолчание довода `false`) и оба режима `yaxunit_tests` решают тем же
правилом.</details>

<a id="infobase_admin"></a>
<details>
<summary><code>infobase_admin</code> - жизненный цикл информационной базы</summary>

Объединяет `get_applications`, `list_registered_infobases`, `read_event_log`, `create_infobase`,
`register_infobase`, `delete_infobase`, `set_infobase_credentials`, `create_launch_config`, `start_client`,
`branch_infobase`, `update_database`, `inspect_database_sync`, `export_database_snapshot`,
`restore_database_snapshot`, `sync_control` и встроенную справку.

`dryRun` объявлен и здесь: через фасад он доходит до `update_database` тем же доводом. `update_database` принимает и `statusOnly`: чтение отслеживаемых обновлений (`runKey`, состояние, прогресс) без порождения прогона. Перед чтением состояния обновление обновляет проект и родителя расширения с диска (`refreshWorkspace`, по умолчанию true): файлы, записанные мимо сервера (файловый инструмент, git checkout, pull), модели иначе невидимы, и ответ несет `workspaceRefresh.changedResources` - число ресурсов, которые перечитывание с диска изменило (добавление, удаление, изменение содержимого); 0 значит модель уже совпадала с диском.

`update_database` пересекает границу, за которой прогон не вернуть. Отмена до входа в блокирующий вызов платформы не дает ему начаться: ответ несет `tag=cancelled`, база остается как была. Отмена после входа вызов не прерывает - ответ говорит, что работа остановлена не была и может продолжать писать. Пока отмененный прогон не завершился, повторный вызов с теми же доводами второй прогон не запускает и отвечает `stillStopping`.

`inspect_database_sync` читает и не меняет ничего: он отвечает блоком `dataLossProtection` с
`nextUpdateProtectsData`, `acceptDataLossDefault=false`, `dataLossCompared`, `pendingDataLoss`,
`pendingDataLossCount`, `baseline`, `dataLossCheck` и `nextStep` (последний - когда потеря найдена), а
`nothingStarted=true` стоит в корне ответа. Обновление базы не переключает настройку
`restructureConfirmationPrompt` (`on`, `off` или `unknown` в ответе) и не показывает окно подтверждения
реорганизации информации: она остается такой, какой ее задал пользователь.

`export_database_snapshot` выгружает информационную базу приложения целиком в `.dt` (`path` обязателен; файл,
уже стоящий по пути, отклоняется тегом `alreadyExists`, а не заменяется): дамп пишется одним запуском толстого
клиента платформы во временный файл рядом с назначением и переносится на место, только когда он непуст и создан
этим прогоном (`outputMissing` иначе). `restore_database_snapshot` загружает `.dt` в базу: сначала пишется копия
текущего содержимого базы (`backupTo`, без него - `<имя файла>-backup-<время>.dt` рядом с загружаемым; занятый
путь копии - `alreadyExists`, отсутствующий или пустой исходный файл - `inputMissing`, и загрузка не
начинается), а загрузка заменяет все, что база держит. Обе операции занимают базу монополией на время прогона
(снимки всех баз идут по очереди), отказ `busy` называет держателей блоком `infobaseHolders`, когда
сервер их видит, - `clients` с конфигурациями запуска, `otherInstances` с соседними экземплярами сервера
и `note`. `timeoutSeconds` 5-120, по умолчанию 30
(псевдоним `waitSeconds`): дольше - ответ `Pending` с `runKey`, повторный вызов с `runKey` ждет дальше,
`cancel=true` снимает отслеживание - запуск, ушедший в платформу, не прерывается, начавшаяся загрузка не
откатывается. Ответ успеха несет `status` (`Exported` / `Loaded`), `path`, `sizeBytes`, `durationMs`,
`infobase`, у загрузки - `backup` и `backupSizeBytes`; отказ загрузки, у которой копия уже записана, тоже несет `backup` и `backupSizeBytes`;
успешная загрузка помечает хранимую копию `ConfigDumpInfo.xml` (`copyMarked: true`, `infobaseChangeCheck`, `nextStep`), и инкрементальное `update_database` отказывает, пока копию не перестроит `rebuild_dump_info`; пометка, которую записать не удалось, - `copyMarked: false` с причиной в `infobaseChangeCheck` и `nextStep`: следующее инкрементальное обновление эту загрузку не увидит, пока копия не перестроена; запуск, брошенный по бюджету в 600 секунд, пока процесс
жив, держит блокировку базы, и ответ называет `lockHeldForProcess`; `leftBehind` (файл, в который
пишет живой процесс) - когда отказ упал на записи временного файла выгрузки или копии загрузки.

Действие `sync_control` передается доводом `syncOperation`: внутренняя операция `sync_control`
(`status`, `diagnose`, `retrieve_database_changes` и другие) не совпадает с маршрутизацией фасада, и без
`syncOperation` вызов отказывает списком действий.
</details>

<a id="config_io"></a>
<details>
<summary><code>config_io</code> - импорт и экспорт</summary>

Объединяет `export_configuration_to_xml`, `import_configuration_from_xml`, `import_configuration_from_binary`,
`export_object`, `export_common_picture`, `export_configuration_to_cf`, `export_infobase_objects`,
`unpack_external_binary`, `export_database_configuration` и `export_database_extension`.

`export_infobase_objects` выгружает выбранные объекты конфигурации **базы** (а не проекта EDT) в иерархический XML Конфигуратора: правки, сделанные в Конфигураторе, становятся видимы агенту. Довод `objects` принимает верхний объект (`Catalog.Банки`, `Справочник.Банки`), форму (`Catalog.Банки.Form.ФормаЭлемента`, русские виды тоже) и общую форму (`CommonForm.Имя`); существование адреса сверяется по модели проекта EDT, прочие дочерние виды отклоняются до запуска Конфигуратора. `outputPath` - абсолютный путь каталога результата, отсутствующий или пустой. Ответ несет `files` (относительные пути по алфавиту), `objects` (адрес -> строка файла списка), `source: "infobase"` и `infobase`. Медленная выгрузка отвечает `Pending` с `runKey`; предел работы Конфигуратора - 600 секунд, отмененная до запуска выгрузка ничего не запускает. Пресеты только-чтения выключают операцию.

`export_database_configuration` и `export_database_extension` выгружают конфигурацию или названное расширение
**базы** в бинарный `.cf` / `.cfe`: занятый `outputPath` отвергается тегом `alreadyExists` без
`overwrite=true`, а база не в состоянии `EQUAL` - тегом `outOfSync` без `allowOutOfSync=true`, чтобы прежний
файл не сошел за результат этого вызова. Выгрузка идет во временный файл, результат принимается только
непустым и новее момента вызова, затем переносится на место. У выгрузки расширения обязателен `extensionName`.
Обе операции синхронные, и `export_configuration_to_cf` с `export_extension` идут тем же путем.

`import_configuration_from_xml` передает версию платформы и базовый проект в порядке API импорта.
`baseProjectName` у обоих импортов называет проект конфигурации, которую расширяет расширение; несуществующий
проект отвергается тегом `projectNotFound` до импорта.

`export_object` и `import_configuration_from_binary` пересекают границу, за которой прогон не вернуть - сборка внешнего объекта и процесс Конфигуратора. Отмена до нее прогон не запускает: ответ несет `tag=cancelled`, файл не пишется, проект не создается. Отмена после - вызов не прерывает, и ответ говорит, что работа остановлена не была. Пока отмененный прогон не завершился, повторный вызов с теми же доводами второй прогон не запускает и отвечает `stillStopping`.
</details>

<a id="cluster_admin"></a>
<details>
<summary><code>cluster_admin</code> - кластеры навигатора</summary>

Кластер - своя папка в навигаторе над коллекцией метаданных (`Catalog`, `CommonModule` и т.п.);
состав каждого кластера хранится в `.settings/aiedt-clusters.yaml` проекта, и объект в кластере
скрывается со своего обычного места в дереве. Служба кластеров не является службой OSGi: до старта
плагина и после остановки ее нет, и каждая операция отвечает `serviceUnavailable`, а не падает.

Операции: `get_clusters` (дерево кластеров: `fullPath`, `name`, `description`, `order`, `objects`,
`children`; с `collectionPath` - одна коллекция, без - все коллекции проекта), `create_cluster`
(`name` + `collectionPath`, либо вложенность под `parentClusterPath`; имя пустое после обрезки
пробелов или со слешем - отказ `invalidName`, отсутствующий родитель - `clusterNotFound`),
`update_cluster` (`newName` обязателен, `description` опционален; занятое имя - `nameTaken`,
повтор того же состояния - `noChange: true`), `delete_cluster` (удаляет вложенные кластеры;
`dryRun=true` отвечает `{deleted:false, nestedClusters:N, objects:M}` без записи, где
`nestedClusters` - кластеры под указанным, `objects` - объекты во всех удаляемых), `add_to_cluster`
(объект переносится из текущего кластера, ответ `{clusterPath, movedFrom}` с `movedFrom: null`,
когда прежнего кластера не было; повтор в тот же кластер - `noChange: true`, не отказ),
`remove_from_cluster` (ответ `removedFrom` со всеми кластерами-держателями; объект вне кластеров -
отказ `notClustered`).

`add_to_cluster` проверяет `objectFqn` по модели EDT до записи: объект не найден - отказ
`objectNotFound` с ближайшими именами той же коллекции, объект другой коллекции, чем кластер
(`Document.X` в кластер `Catalog`) - отказ `outsideCollection`. Коллекция кластера - первый сегмент
его полного пути; тип объекта - первый сегмент FQN.

Отказ записи несет `reason` с кодом исхода как есть (`clusterNotFound`, `clusterExists`,
`nameTaken`, `changedOnDisk`, `unreadableFile`, `notReadByThisStore`, `readFailed`, `lockRefused`,
`accessDenied`, `writeFailed`) и текст для человека; все доводы проверяются до записи.

Пять записей (`create_cluster`, `update_cluster`, `delete_cluster`, `add_to_cluster`,
`remove_from_cluster`) выключаются пресетами Read-only, Debug & Test и Code Review каждая своей
дверью и отвергаются до чтения файла кластеров; `dryRun` удаления проходит ту же дверь.
</details>

<a id="tag_admin"></a>
<details>
<summary><code>tag_admin</code> - запись меток</summary>

Метка - имя с цветом и описанием, которое навешивается на объекты метаданных; определения и назначения
лежат в `.settings/aiedt-markers.yaml` проекта. Чтение (список меток, объекты по меткам) остается в
`workspace_marks`, этот фасад только пишет. Служба меток - ленивый синглтон, но ответ `serviceUnavailable`
заложен на случай, когда ее нет.

Операции: `create_tag` (`tag` обязателен; `color` в виде `#RRGGBB`, иначе отказ `invalidColor`; без `color` -
серый по умолчанию), `update_tag` (`newName`, `color`, `description`; отсутствующий довод оставляет поле как
есть, пустая строка `description` очищает его; переименование переносит назначения, ответ называет
`movedAssignments`), `delete_tag` (снимает метку со всех объектов, ответ `assignments` - число снятых;
`dryRun=true` отвечает `{deleted:false, assignments:N}` без записи), `assign_tag` (`objectFqn` + массив `tags`:
объект проверяется по модели EDT - вложенные адреса вида `Catalog.X.Attribute.Y` и `Catalog.X.Form.F`
разбираются по парам вид-имя; список пишется одной записью, одна неизвестная метка - отказ всего вызова,
пустой либо пробельный элемент массива - отказ `invalidName` всего вызова; уже назначенная метка не отказ, а
`skipped` с `reason: alreadyAssigned`), `unassign_tag` (массив `tags`: не назначенная - `skipped` с
`reason: notAssigned`; не снято ничего - `isError` с `reason=notAssigned`). Ответ `assign_tag` и `unassign_tag`
называет то, что сама операция изменила под блокировкой записи: метка, назначенная параллельным вызовом
раньше, попадает в `skipped`, а не в `assigned`/`removed`.
Имена, различающиеся регистром, - разные метки; имя пустое после обрезки пробелов - отказ `invalidName`.

Файловые отказы у всех пишущих: `unreadableFile` (файл не парсится), `readOnlyFile`, `changedOnDisk` (файл
изменился после чтения - запись отвергнута, файл не тронут), `saveFailed` (в том числе когда байты файла
не читаются вовсе - отказ доступа, недоступный диск). Все доводы проверяются до записи,
отказ - `isError` с полем `reason` и текстом для человека.

Пять записей выключаются пресетами Read-only, Debug & Test и Code Review каждая своей дверью и
отвергаются до чтения файла меток; `dryRun` удаления проходит ту же дверь.
</details>

<a id="yaxunit_tests"></a>
<details>
<summary><code>yaxunit_tests</code> - запуск и отладка YAxUnit</summary>

Поддерживает обычный запуск и debug-режим. Требует установленного расширения YAxUnit и конфигурации запуска целевой ИБ.

Перед запуском читается `updateBeforeLaunch` (по умолчанию true): не завершившееся обновление базы отказывает,
называя `updateBeforeLaunch=false` способом запустить без обновления. Пресет, выключивший `update_database`
(Read-only, Debug & Test, Code Review), с явным `true` отказывает оба режима до обновления и до запуска, а
вызов без довода запускает без обновления; каждый ответ такого прогона - готовый, `Pending` и поднятый
повторным вызовом - несет `databaseUpdate=SKIPPED_BY_PRESET` с пояснением `databaseUpdateNote`.
Довод `reuseRecent` (по умолчанию false,
читается только при `mode=run`) отвечает результатом прогона, завершенного за последние 5 минут, с полем
`cached: true` и пометкой с временем завершения. Прогон, начатый этим же сервером и еще не выданный,
забирает вызов без пометки: такой вызов считается первым, пишет квитанцию и отдает отчет как свой
результат; `cached` и пометку несет тот же отчет, отданный повторно, или отчет из кеша, и пометка называет
причину - запрошенный свежий отчет либо прогон, чей результат не забрали. `suites`, `tags` и `contexts` в
обоих режимах отказывают: они не сужают фильтр конфигурации запуска.

Завершенный прогон (`mode=run`) оставляет квитанцию: в ответе есть `receiptPath` - путь JSON-файла в `run-receipts/yaxunit_tests` внутри каталога состояния плагина. Квитанция несет время прогона (`at`), проект (`projectName`), фильтры вызова (`mode`, `extensions`, `modules`, `tests`), числа результата (`total`, `passed`, `failures`, `errors`, `skipped`) и путь отчета (`reportPath`); те же числа и `reportPath` есть и в самом ответе. В каталоге остается не больше 20 последних квитанций инструмента. Отказ до запуска квитанции не пишет; если каталог состояния недоступен, ответ несет `receiptError` вместо `receiptPath`, а поля результата остаются на месте.
</details>

<a id="edit_metadata"></a>
<details>
<summary><code>edit_metadata</code> - универсальный конструктор метаданных</summary>

Пишущие операции гасятся пресетами Read-only, Debug & Test и Code Review дверью
`edit_metadata_writes` и отвергаются до чтения проекта; батч с пишущими операциями не стартует
целиком, заблокированные записи названы в `presetBlocked`. Чтения (`help`, `get_template_content`,
`get_route_map`, `list_pictures`, `list_form_appearance_rules`) и `dryRun` работают. У `sync_export`,
`remove_object`, `delete_metadata_object` и `rename_metadata_object` предпросмотра нет: они отвергаются и с
`dryRun=true`. Отказ называет фасад и пресет.

Содержит около 160 операций, разбитых на домены:

- объекты и их вложенные элементы;
- специализированные типы метаданных;
- командный интерфейс;
- HTTP- и SOAP-сервисы;
- управляемые формы;
- макеты;
- карта маршрута бизнес-процесса;
- расширения;
- СКД;
- общие пакетные и служебные операции.

Поддерживает `dryRun`, пакетное выполнение и `operation=help`. Полный список следует получать из встроенной справки, поскольку это самая быстро меняющаяся часть API.

**Холостой прогон и запись под поддержкой.** Холостой прогон (`dryRun=true`) ничего не заимствует:
`add_object_attribute` и `add_tabular_section_attribute` целей ссылочных типов не заводят,
`add_metadata_attribute` читает `dryRun`, а заимствование в расширение отвечает планом `wouldBorrow` с
причиной `dryRun`. Ответ холостого прогона несет `dryRun: true` - и на успехе, и на отказе - у записи в объект
метаданных, у схемы и у настроек динамического списка; операции уровня формы (`add_form_event_handler`,
`set_form_item_property`, `add_form_command`) поля `dryRun` не кладут, а `remove_item` и
`add_form_appearance_rule` - только на успехе.

Операции записи отказывают до открытия транзакции, когда объект закрыт реестром поддержки
(`ChangesNotAllowed`): закрытость решает не один ответ реестра, а оба ответа сразу - запись реестра и ответ
среды, что править она не станет; служба, не ответившая на вопрос, и `canEdit=true` запись не останавливают.
Отказ называет FQN объекта, записанный режим, `canEdit` и подсказку снятия защиты, тег
`supportLock`. Вложенная подсистема (`Subsystem.A.Subsystem.B`) судится по собственной записи поддержки, а не
по родителю. Чтения (`get_form_structure`, `list_named_areas`, `read_template`, `check_print_width` и
подобные) вопроса поддержки не задают.

Удаление реквизита, табличной части или реквизита табличной части отвергается тегом `requiresCascadeForms` со
списком форм и элементов, когда элемент формы владельца держит путь данных на удаляемое; `cascadeForms=true`
снимает эти элементы в той же транзакции, называет их в `formItemsRemoved` и выгружает формы; при `dryRun`
выгрузки нет, и `formExportWarning` в ответе не появляется. Путь сравнивается точно от главного реквизита
формы, а у формы без главного реквизита - от `Object` и `Объект`. Квалификатор, которого не принимает ни один
тип состава (`length` у `Number`), в операциях реквизитов объектов отказом не становится: ответ несет
`qualifierIgnored`;
в СКД такой квалификатор отвергается и ничего не пишет.

**Значение заполнения.** `setObjectProperty propertyName=fillValue` строит значение по единственному типу
реквизита: `true`/`false` для булева, число, строка (длиннее объявленной длины - отказ с названной длиной),
дата в формате `YYYY-MM-DD` при квалификаторе "дата", `YYYY-MM-DDTHH:MM:SS` при "дата и время", `HH:MM:SS`
при "время" - несоответствие квалификатору отвергается; для типа-перечисления - имя значения
(`Обычная` или `Enum.ВариантыВажностиЗадачи.EnumValue.Обычная`, без учета регистра), для ссылочного типа -
имя предопределенного элемента; литерал `EmptyRef` (`ПустаяСсылка`) дает пустую ссылку типа,
`StandardBeginningDate` (`НачалоДаты`) - начало даты `0001-01-01T00:00:00`. Пустое значение или `Undefined`
(`Неопределено`) снимает значение заполнения. Составной тип отвергается, неизвестное имя - отказ с ближайшими
подходящими. `get_metadata_details` в широкой таблице реквизитов показывает записанное значение колонкой
Fill Value (для ссылочного - FQN значения).

В пакете провал, следующий из того, что прежняя операция не создала объект (из-за `dryRun` или ошибки),
помечен `derivedFailure` и `causedByOperation`, а холостой пакет отвечает "Nothing was written" вместо
"already applied".

**Заготовки и оформление формы.** `add_form_event_handler` и `add_command_handler` дописывают
процедуру-обработчик в модуль формы (`writeStub`, по умолчанию true) и отвечают `stubWritten`,
`stubSkippedReason` (`alreadyPresent` или `dryRun`), `modulePath` и `stubError`; `remove_form_event_handler`
модуль формы не трогает: `moduleProcedure` напоминает снять процедуру через `write_module_source`, когда
ее больше никто не вызывает. Заготовка пишется в область модуля (`ОбработчикиСобытийФормы`,
`ОбработчикиСобытийЭлементовШапкиФормы`, `ОбработчикиСобытийЭлементовТаблицыФормы<Имя>`,
`ОбработчикиКомандФормы` или их английские имена) перед ее закрывающей директивой, а если области нет -
создается в конце модуля на языке модуля; ответ называет область в `stubRegion` и ее создание в
`stubRegionCreated`. Существующая процедура с другой директивой или числом параметров отмечается
`existingProcedureMismatch`.

`remove_item` удаляет элемент формы по `formFqn` (или `containerFqn` как его синониму) и `name`, ищет элемент
по всей форме и сообщает успех, только когда элемент снят; `dryRun` поддерживается, а макет и объект
метаданных отвергаются с именем операции.

`add_form_command_interface_item` разрешает адрес команды в объект `Command` до создания элемента и отказывает
тегом `formApiNotFound`, если адрес не нашел команду, - панель остается нетронутой. Принимаются адреса
`Form.Command.<Имя>`, `Form.StandardCommand.<Имя>`, `Form.Item.<Элемент>.StandardCommand.<Имя>`,
`CommonCommand.<Имя>`, `<Тип>.<Объект>.Command.<Имя>` и `<Тип>.<Объект>.StandardCommand.<Имя>` без учета
регистра; адрес вложенного элемента интерфейса команд разрешается по самому адресу, без поиска названного
элемента, а обходом контейнера адресуется связанная команда при поиске элемента панели; `group`, `visible` и
`index` применяются как типы, которые принимают их сеттеры; группа, которую уже несет другой элемент панели,
используется как есть.

`add_form_appearance_rule` (`itemNames` - элементы формы через запятую, пусто - вся форма; условие `field`,
`conditionType`, `conditionValue` и `appearance` как у `add_conditional_appearance`),
`list_form_appearance_rules` и `remove_form_appearance_rule` (`index` или `field`, в том числе внутри групп
условий) пишут правила в `ConditionalAppearance.dcssca` рядом с `Form.form`; ошибка записи файла приходит
полем `persistWarning`. `list_form_appearance_rules` отдает цвет как `#RRGGBB`, шрифт как
`Face,height[,bold][,italic]`, а группу условий - как `groupType` с `items`.

`set_excluded_commands` убирает стандартные команды из интерфейса команд объекта формы: `itemPath` называет
объект - саму форму (`Form` или пусто), источник глобальных команд (`FormCommandPanelGlobalCommands`) или
элемент (`Item.<Имя>` или просто имя), `commands` - имена команд без учета регистра. `mode` равен `replace`
(по умолчанию: список становится ровно переданным, и пустой `commands` очищает его), `add` или `remove`;
`add` и `remove` требуют хотя бы одного имени. Список ведут только форма, таблица, поле и источник глобальных
команд: командная панель, контекстное меню и группа кнопок отвергаются с адресом источника, из которого они
берут команды. Каждое имя сверяется со списком `getCommands()` самого объекта до записи, имя вне списка
отвергается с перечнем допустимых и ближайшим совпадением, а новые элементы берутся из того же списка, а не
создаются. Объект с непостроенным списком команд отвергается своими словами. Ответ несет `excludedCommands`
(итоговый список в порядке модели), `added`, `removed` и `changed`; результат, равный уже стоящему списку,
отвечает `changed: false` и ничего не пишет. Отказ несет `availableCommands`.

`list_pictures` отдает стандартные картинки версии платформы проекта: `stockPictures` и `stockExtPictures` с
числами, `filter` ищет по английскому и русскому имени; без реестра картинок отказ `serviceUnavailable`. Имена
`StdPicture.<Имя>` и `StdExtPicture.<Имя>` проверяются по тому же списку и русское имя принимается;
`add_decoration elementType=Picture` и `set_form_item_property picture` записывают картинку ссылкой
`PictureRef`, а русское имя стандартной картинки пишется английским; картинка, которую нельзя построить,
отказывает, и декорация не добавляется.

**Создание объектов и макетов.** `create_form` с `setAsDefault` ставит свойство формы по умолчанию по
назначению формы (`defaultListForm` для списка и так далее), а форма без сеттера попадает строкой в
`formSetterWarnings`; пустая управляемая форма (`layout=empty`) получает на корне внутренней формы
свойства генераторной формы: `SaveWindowSettings`, `AutoTitle`, `AutoUrl`, `Group=Vertical`,
`AutoFillCheck`, `AllowFormCustomize`, `Enabled`, `ShowTitle`, `ShowCloseButton` - все `true`, кроме
`Group`, - плюс `autoCommandBar` с `horizontalAlign=Left` и `autoFill=true` (панель, которой у формы не
было, создается с именем `ФормаКоманднаяПанель` и `id` -1) и пустой `commandInterface` с панелями
навигации и команд; то же получает внутренняя форма общей формы. `formScaffolded` в ответе -
число поставленных свойств, и поле появляется, только когда оно не ноль; свойство без сеттера на текущей
сборке EDT пропускается молча; отказ
`create_form` поля `message` не несет - `message` ставится только в успешном ответе. `formName` и имя
владельца - один элемент пути, иначе отказ до записи.

`create_object` строит справочник или документ через проектную фабрику модели, тем же маршрутом, что
мастер EDT, и объект получает умолчания мастера своего вида: у справочника уровень, длины кода и
наименования, вид кода, уникальность кода, автонумерация, группы сверху; у документа длина и вид номера,
периодичность, уникальность номера, автонумерация, проведение; у обоих стандартные команды и
`producedTypes`. Если эта фабрика недоступна, создание идет через сырую фабрику, а ответ несет `warning` с
перечнем умолчаний, которых объект не получил, и причиной.

`create_object` с `objectType=CommonTemplate` ставит `templateType=SpreadsheetDocument`, если свойства не
задали другой тип, и после записи создает пустой `Template.mxlx`. Ответ несет `templateType` и
`templateContentCreated`; когда `Template.mxlx` уже был в каталоге макета, файл не меняется и ответ несет
`templateContentKept` с `templateContentNote`. Если файл не записался, ответ несет `templateContentInitWarning` и называет
`mxl_workshop create_template` с `ownerFqn=CommonTemplate.<Имя>` и `templateName=<Имя>`. Тип
`TextDocument` и прочие файл макета не получают. `dryRun` файл не пишет.

`add_predefined_item` пишет `code` у справочника и плана видов расчета значением по типу кода владельца (число
или строка). Нечисловой код при числовом типе, занятый код и нечитаемый тип кода отвергаются до записи, а
отказ называет владельца как `Вид.Имя`.

`add_template` сверяет `templateType` с литералами модели до транзакции и отказывает на неизвестном; ответ
несет в `templateType` тип, записанный моделью, и `requestedTemplateType` - запрошенный тип, приведенный к литералу модели, когда записанный тип от него
отличается;
синонимы (`GraphicalScheme`, русские названия) приводятся к литералу модели (`GraphicalSchema`); FQN владельца с русским видом переводится по каталогу типов, а имя владельца и имя макета
- один элемент пути; `set_template_content` с явным `templateType` отказывает на макете без каталога и с
другим форматом.

**Карта маршрута и адресация задачи.** `get_route_map` отвечает `title`, `taskDescription`,
`subprocess`, `location` (`top`/`left`/`bottom`/`right`), `addressingAttributes` и `events` (`event`
и `handler`) каждой точки, `title` перехода, когда файл его несет, и `branch` для перехода из
`Condition`; свойство, которого схема не несет, в точку не попадает. `create_route_map` читает
`location` точки (четыре стороны либо `x`/`y` с необязательными `width` и `height`) и `handlers`
(объект событие-обработчик либо массив `{event,handler}`), отказывает на событии, которого вид точки
не объявляет, на пустом имени обработчика и на неполном `location`, и отвечает `replaced`, `points`
с записанными координатами и `locationFromCaller`, `handlers`, `stubsWritten` и
`stubsAlreadyPresent` (при `dryRun` - `stubsToWrite`); обработчик, которого модуль объекта
бизнес-процесса не объявляет, получает процедуру с параметрами своего события, а при нечитаемом
модуле не добавляется, и причина приходит в `stubWriteFailed`.

`set_task_addressing` пишет `addressingRegister`, `addressingAttributes`, `mainAddressingAttribute` и
`currentPerformer` задачи (или задачи, с которой связан бизнес-процесс); вызов, не назвавший ни одного из
четырех, отказывает со списком. Недостающий реквизит адресации создается с типом и измерением из записи;
реквизит без указанного измерения привязывается к одноименному измерению регистра адресации, а реквизит без
такого измерения отвергается со списком измерений регистра. Каждое свойство перечитывается в той же
транзакции, и несовпадение при перечитывании отвергает вызов; при `dryRun=true` ответ говорит, что запись
прочитана и откатана, и не записано ничего.

**События формы.** У корня формы два контейнера обработчиков, и событие определяет, в какой из них попадет обработчик: события записи и чтения объекта (`OnWriteAtServer`, `BeforeWriteAtServer`, `AfterWriteAtServer`, `OnReadAtServer`, `BeforeWrite`, `AfterWrite`), а также события настроек и вариантов отчета живут в `extInfo` формы; `OnCreateAtServer`, `OnOpen`, `NotificationProcessing`, `FillCheckProcessingAtServer` и прочие - на самом корне. `add_form_event_handler` выбирает контейнер сам и **отказывает, если событие уже обработано**, называя имя обработчика и контейнер: платформа вызывает один обработчик на событие, и второй дает не второе поведение, а неопределенное. `remove_form_event_handler` ищет в обоих контейнерах.

**Путь данных в форме расширения.** Операции, назначающие элементу формы путь данных (`add_field`, `add_table` и `add_form_attribute_column` с `dataPath`, `set_property` и `set_form_item_property` со свойством `dataPath` и со свойствами-путями вроде `footerDataPath`), на форме проекта расширения заимствуют реквизит основной формы, с которого путь начинается, в той же записи; ответ называет заимствованное в `adoptedFormAttributes` (поле есть, только когда список не пуст). Путь, который не будет выгружен с формой расширения и при этом не разрешается самой формой, не записывается: ответ - отказ с именем элемента, путем и причиной, форма остается без изменений. Путь, который операция создает сама (`add_dynamic_list_table`, `setup_settings_composer_on_form`), о разрешении не спрашивается - объект принадлежит этой же записи. Вопрос, который среде задать не удалось (служба недоступна, вызов упал), отказом не становится: запись проходит, а ответ называет непроверенное в `dataPathChecksNotPerformed` (`attributeBelongsToExtension`, `exportOfExtensionForm`, `pathResolutionInForm`); поля нет, когда спрошено все. Путь, который форма разрешает, но на который расширение сослаться не может (сегмент чужого движка, хвост за заимствованным реквизитом), принимается и при выгрузке может быть потерян без предупреждения: проверка EDT `form-data-path` срабатывает только на неизвестный сегмент. Форм конфигурации это не касается.
</details>

<a id="dcs_workshop"></a>
<details>
<summary><code>dcs_workshop</code> - схема компоновки данных</summary>

Создает и изменяет наборы данных, поля, параметры, связи, вычисляемые поля, ресурсы, настройки и варианты отчета. Проверяет запросы и выражения перед записью.

Все операции, кроме `help`, пишут схему или настройки и гасятся пресетами Read-only, Debug & Test
и Code Review дверью `dcs_workshop_writes` - до захвата UI-потока и BM-транзакции; `help` и
`dryRun` работают.

`add_parameter` и `set_parameter` (через фасад - `edit_metadata add_schema_parameter` и
`set_schema_parameter`) пишут `expression`, `use`, `valueListAllowed` и `denyIncompleteValues`; квалификаторы
`length`, `precision`, `fractionDigits`, `nonNegative`, `dateFractions` и `allowedLength` применяются к типу
значения параметра. Квалификатор без `type` и неразрешимый тип - отказ, при котором не записано ничего. `use`
принимает `true`/`Always`/`Всегда` как Always и `false`/`Auto`/`Авто` как Auto, иное - отказ. Поле, которое
параметр не принял, отвергается ответом "Nothing was written", а не успехом. `set_settings_parameter` без
`value`, `userSettingID` и `use` отказывает и литерал не трогает.

`set_output_parameter` создает контейнер параметров вывода и запись параметра, когда настройки их не несут, а
без `value` отказывает. Имя сверяется с перечнем параметров вывода платформы в обоих написаниях: неизвестное
отвергается с ближайшим именем и перечнем доступных (`Available:`; перечень длиннее 40 имен - первые 40
и `(+N more)`), запись идет в написании платформы, а существующая запись
находится по обоим написаниям. Если перечень прочитать не удалось, запись выполняется, а ответ несет
`outputParameterNameChecked: false` и `outputParameterNameCheckNote`.

`add_field` пишет `title`, `type` и пару `property`/`value`, где `property=type` читается как тип; неизвестное
свойство и неприменимый тип отвергаются до добавления поля. `remove_dataset` снимает набор данных и вместе с
ним вычисляемые и итоговые поля, в выражении которых имя набора стоит отдельным словом с точкой после него
(`Sales.Amount`, `Sum(Sales.Amount)`), без учета регистра.
`remove_query_condition` снимает соседний AND, И, OR или ИЛИ, а условие между AND и OR отвергает. Шаг
`parentPath` находится без учета регистра. Неизвестный литерал `comparisonType`, `conditionType`, `orderType`
или `groupingType` отвергается со списком `Allowed:`. `set_dataset_link_property` отвергает свойство, которого
у связи нет, и значение, которое сеттер не принял, называя связь и свойство.

`remove_conditional_appearance` читает `target`: `schema` и `settings` - настройки варианта по умолчанию,
иное - имя варианта настроек, а неизвестный вариант отвергается по имени (`notFound`, `kind=settingsVariant`).
`add_conditional_appearance` довод `target` не читает и всегда пишет в настройки варианта по умолчанию.
Удаление, не нашедшее оформления, контейнер не создает. `add_settings_table` и `add_settings_chart`
пишут ресурсы, объявленные схемой, в выбранные поля элемента структуры и называют их в ответе; схема без
ресурсов отвечает, что ничего не выбрано, а не голым успехом; ресурс читается из `dataPath` итогового поля, и
путь, общий для нескольких итогов, выбирается один раз; уже заполненная выборка остается без изменений.

`remove_dataset`, `remove_dataset_field`, `remove_parameter`, `remove_calculated_field` и `remove_total_field`
читают все варианты настроек схемы и называют в `affectedSettings` выборку, порядок, фильтр, структуру,
условное оформление и параметры данных, которые еще ссылаются на удаляемый элемент, - сами настройки при этом
не меняются. Довод `reportAffectedSettings` (по умолчанию true) со значением false списка не выводит. Путь
поля, составленный из имени набора данных (`Sales.Customer.TaxId`), распознается в списке как один
идентификатор независимо от того, что несет путь.

Операции, которые пишут настройки (отборы, параметры данных, варианты, копирование варианта), после записи называют в поле `settingsWarnings` то, что осталось незаполненным: элемент отбора с `use=true` и пустым правым значением при виде сравнения, который требует значения (`emptyFilterValue`; «Заполнено» и «Не заполнено» значения не требуют), и параметр данных со стандартным периодом «Произвольный» без дат (`emptyPeriod`). Это предупреждение, а не отказ: запись выполнена. Проверяются все настройки варианта, в который шла запись, а не только записанный элемент; `variant` - имя варианта либо `default` для настроек схемы по умолчанию и для динамического списка формы, `path` - путь к элементу, `name` - поле отбора или имя параметра. Нарушений нет - поля нет.

`repair_schema` (через фасад - `edit_metadata operation=repair_report_schema`) восстанавливает схему из `.dcs` в модель. Доводы: `projectName`, `objectName` (владелец или полный FQN схемы), `templateName` (по умолчанию - основная схема владельца на языке конфигурации), `overwriteModel`, `dryRun`. Файл не изменяется. Исходы в поле `outcome`: `restored` - в модели схемы не было, схема из файла подключена; `matched` - модель уже сериализуется в байты файла, ничего не изменено; `refused_model_differs` - в модели другая схема (`modelBytes`, `fileBytes`, `firstDifferenceAt`), с `overwriteModel=true` она записывается в `backupPath` рядом с `.dcs` и заменяется (`replaced`); `file_changed` - файл изменился между чтением и подключением, ничего не изменено; `no_template` - объект макета не объявлен; `no_file` - `.dcs` нет. При `dryRun=false` успех решает прочтение модели после фиксации:
она должна сериализоваться в байты файла; успешный ответ несет `confirmed: true`, а если прочтение изменение не
подтвердило, вызов отказывает и причину называет `confirmation`. При `dryRun=true` успех решают предпросмотр и
решение, поля `confirmed` в ответе нет; у отказа до фиксации причина - в тексте ошибки вместе с `outcome`. С `dryRun=true` операция решает и отвечает, не меняя модель и не записывая копию; путь копии, которая была бы записана, - в `plannedBackupPath`. `fileChangedDuringRepair` - файл изменился за время вызова.
</details>

<a id="mxl_workshop"></a>
<details>
<summary><code>mxl_workshop</code> - табличный макет MXL</summary>

Управляет областями, ячейками, объединением и рисунками табличного документа. Пишущие
операции гасятся пресетами Read-only, Debug & Test и Code Review дверью `mxl_workshop_writes` и
отвергаются до чтения проекта; `read_template`, `list_named_areas`, `check_print_width`, `help` и
`dryRun` работают. `format_cells` задает оформление: перенос текста (`textPlacement`), поворот (`textOrientation`), высоту строки, ширину колонки, автоширину и вес колонки при распределении ширины. Именованные области: `list_named_areas` перечисляет их с координатами, `add_named_area` задает область по диапазону строк и колонок, `remove_named_area` удаляет; `read_template` возвращает `namedAreas`. Поддерживает preview через `dryRun`.

`insert_rows`, `delete_rows` и `copy_rows` работают строками целиком. `insert_rows` вставляет `count` строк перед `row` (допустима последняя строка + 1): все, что стоит в этой строке и ниже, сдвигается вниз - строки с ячейками и примечаниями, объединения (в том числе объединения целых строк), именованные области, группы строк, рисунки, области печати и повторения, объявленная высота и сохраненные строки просмотра. Объединение, область, группа или рисунок, в которые попала точка вставки, растягиваются, а не сдвигаются. `formatFrom` задает, откуда новые строки берут формат строки и форматы ячеек: `above` (умолчание; при `row=1` - как `none`), `below`, `none`; текст, параметры и расшифровки не копируются. `delete_rows` удаляет `count` строк с `row`: нижние сдвигаются вверх; объединения, области и рисунки, целиком лежащие в диапазоне, удаляются и называются в ответе (`removedMerges`, `removedNamedAreas`, `removedDrawings`), частично пересекающие - сжимаются. `copy_rows` заменяет `count` строк приемника начиная с `toRow` копией строк источника начиная с `fromRow`: формат строки, ячейки с текстом, параметром, расшифровкой и форматом, примечания; объединения, целиком лежащие в строках источника, повторяются над приемником, целиком лежащие в заменяемых строках приемника, перед этим снимаются. Сдвига нет, пересечение диапазонов источника и приемника - отказ, именованные области не копируются и не меняются; приемник может выходить за текущий конец документа. Ответ несет `shiftedRows`, `resizedMerges`, `removedMerges`, `resizedNamedAreas`, `removedNamedAreas`, `removedDrawings` и `lastRow` после операции.

`insert_columns`, `delete_columns` и `copy_columns` работают столбцами целиком. `insert_columns` вставляет `count` столбцов перед `col` (допустим последний столбец + 1): вправо сдвигаются ячейки каждой строки с примечаниями, наборы колонок с объявленным размером (набор, общий для нескольких строк, сдвигается один раз), объединения (в том числе объединения целых столбцов), именованные области, группы столбцов, рисунки, область печати и повторяемые при печати колонки, сохраненные колонки просмотра. Объединение, область, группа или рисунок, в которые попала точка вставки, растягиваются, а не сдвигаются. `formatFrom` задает, откуда новые столбцы берут формат колонки (ширину) и форматы ячеек: `left` (умолчание; при `col=1` - как `none`), `right`, `none`; текст, параметры и расшифровки не копируются. `delete_columns` удаляет `count` столбцов с `col`: правые сдвигаются влево; объединения, области и рисунки, целиком лежащие в диапазоне, удаляются и называются в ответе, частично пересекающие - сжимаются. `copy_columns` заменяет `count` столбцов приемника начиная с `toCol` копией столбцов источника начиная с `fromCol`: ширина и формат колонки, ячейки с текстом, параметром, расшифровкой и форматом, примечания; объединения, целиком лежащие в столбцах источника, повторяются над приемником, целиком лежащие в заменяемых столбцах приемника, перед этим снимаются. Сдвига нет, пересечение диапазонов источника и приемника - отказ, именованные области не копируются и не меняются; приемник может выходить за текущий конец документа. Ответ несет `shiftedColumns`, `resizedMerges`, `removedMerges`, `resizedNamedAreas`, `removedNamedAreas`, `removedDrawings` и `lastColumn` после операции.

`set_cell` принимает `fillType` и `parameter`, а `format_cells` - границы, шрифт, цвета, узор и параметры
печати; вызов `format_cells` только с параметрами печати диапазона ячеек не требует. `textOrientation`
задается в градусах от 0 до 360, и `read_template` отдает угол в градусах. Первый созданный формат попадает в
файл макета, слот 0 остается пустым плейсхолдером. Смена шрифта копирует шрифт, которым ячейка фактически
отображается (свой, затем строки, затем колонки, затем формат по умолчанию), и привязка к стилю сохраняется.
`set_cell` отказывает на тексте с `parameter` и на имени параметра с заливкой `template`; `format_cells`
отказывает на `fillType` и `parameter` - это доводы `set_cell`. Нечисловые `borderWidth`, `scale`, `copies`
и `perPage` отвергаются. Отступы `topMargin`, `leftMargin`, `bottomMargin` и `rightMargin` принимают
дробные числа миллиметров и отвергают нечисло, отрицательное значение и значение больше
`Integer.MAX_VALUE / 100` мм - столько удержит целое модели, хранящее сотые доли миллиметра; `fontSize`
принимает дробное число пунктов.

`check_print_width` отвечает по одной модели, без платформы, поместится ли область печати на лист по ширине, и называет допущения, на которых стоит ответ. Ширина содержимого - ширина набора колонок, который печатает платформа: колонки документа и наборы колонок строк сравниваются (каждый считается до объявленного размера набора, а не до последней ячейки), побеждает ширейший; область колонок измеряется по колонкам строки 0 (их читает пагинатор), а не по набору, который несет сама область; прямоугольная область считается по x..x+width-1, как масштаб по ширине, а при страничной разбивке платформа берет на одну колонку больше. Ширины колонок берутся по порядку: собственный формат колонки, формат набора колонок, формат по умолчанию документа, затем стандартные 72 восьмых символа. Ширина одного символа измеряется в шрифте макета (Arial 8), и поле `charWidthSource` называет источник величины: у макета вблизи границы ответ зависит от шрифта машины. Настройки страницы, которых модель не задавала, подставляются как у платформы (A4, книжная, поля по 10 мм, масштаб 100%) и перечисляются в `assumed`; бумага, заданная размерами (код -1 с pageWidth и pageHeight в мм), измеряется по ним, а прочие коды, кроме A4, - как A4, и `assumed` это называет. Поле `verdict`: `fits`; `borderline` - ширина превышает доступную не более чем на 5%, и смена шрифта переворачивает ответ между `fits` и `borderline`; `overflows`; `smallPrint` - при `fitToPage` требуемый масштаб ниже `smallScalePercent` (10..100, по умолчанию 75); `empty` - в макете нет ни одной ячейки. Ответ несет `contentWidthMm`, `contentWidthCharUnits`, `printableWidthMm`, `marginMm` и `overflowMm` (одна величина и ее отрицание), `orientation`, `paper`, `printScalePercent`, а для `fitToPage` еще `requiredScalePercent` и `fontSizeAfterScale`. Масштаб печати, записанный в модели, возвращается как `printScalePercent` и в расчет ширины не входит. Операция ничего не изменяет.

Пока проект не готов, запись макета отказывает той же фразой готовности, что `update_database` и
`validate_query`, и файл не меняется. Чтение отказывает той же фразой, пока проект собирается, пока
состояние сборки нельзя определить и пока проект закрыт. Если `Template.mxlx` на диске не пуст, а модель не содержит строк,
набора колонок и рисунков, запись отказывает и файл остается байт в байт; чтение называет расхождение
полем `templateModelFileMismatch`. Пустой каркас макета (тот же XML, что пишет создание, и тот же каркас
с `<indexTo>1</indexTo>` сразу после `<index>0</index>`) расхождением не считается.

Ссылка картинки, которая в проекте не разрешается, останавливает запись до изменения документа и
файла: модель и `Template.mxlx` остаются как были, `dryRun` отвечает тем же отказом; ответ называет
число и первые имена. Пустая ссылка без картинки запись не останавливает. Документ без набора
колонок перед записью получает набор размера 0, как у пустого макета.

`create_template` с `ownerFqn=CommonTemplate.<Имя>` и тем же `templateName` создает общий макет типа
табличного документа и пустой `Template.mxlx`. Существующий общий макет не перезаписывается. Другое
`templateName` отказывает до обращения к модели.
</details>

<a id="extension_workshop"></a>
<details>
<summary><code>extension_workshop</code> - расширения конфигурации</summary>

Объединяет установку, удаление, просмотр и экспорт расширений, lifecycle-сценарии, сравнение с
основной конфигурацией и список перехватчиков. `borrow_object` принимает `includeChildren` (по
умолчанию false): `true` заимствует и собственные подчиненные объекта - реквизиты, в том числе
реквизиты табличных частей, формы, макеты, команды, вложенные подсистемы. Модули не
переопределяются, предопределенные не входят, чужой объект по ссылке типа не обходится: если среда
принесла его сама, он в `pulledByType`, не в `children`. Стандартный реквизит - в `skipped` с
`notAdoptable`. Уже заимствованный корень со связью или с непроверяемой связью не отказ, и потомки
добираются; объект, про который известно, что связи нет, - отказ: ответ несет `alreadyBorrowed` с
причиной, а потомки не обходятся. Значение вне `true`/`false`/`1`/`0`/`yes`/`no` отвергается до
заимствования. Остальные операции фасада довод не читают; `borrow_objects` его не принимает. Правила
- в `operation=help topic=borrow_object`.

`update_borrowed` сверяет заимствованное расширения с обновленной основой: реквизиты и реквизиты
табличных частей - по uuid из `extendedConfigurationObject` и по составу контролируемых типов
(элементы состояния `Checked`) с квалификаторами, формы - по именам элементов (та же модель, что
читает `get_form_structure`), перехватчики - по подписи обработчика. Статусы строк: `inSync`,
`baseWider` (основа шире контролируемого состава, квалификаторы общих типов не разошлись),
`typeConflict`, `sourceGone` (uuid в основе нет), `renamedInBase` (uuid есть, имя другое),
`formOutOfDate`, `handlerSignatureChanged`. `objectFqn` ограничивает обзор одним заимствованным
объектом (нет такого - отказ `reason: objectNotFound` с ближайшими именами); `baseProjectName`
по умолчанию - родительская конфигурация расширения. `apply=true` записывает только `typeConflict`
(точный тип основы с квалификаторами; для составной основы со ссылочными типами - один `AnyRef`
без квалификаторов, той же формой, какой пишет сама среда при заимствовании) и `formOutOfDate`
(через `updateAdopted` сервиса заимствования, после проверки `isUpdatable`). `inSync`, `baseWider`,
`sourceGone`, `renamedInBase` и `handlerSignatureChanged` не пишутся никогда - они перечисляются
в `notApplied` с причиной. Ответ `apply` несет `updatedTypes`, `formsUpdated`, `notApplied` и
`stillOutOfSync` - повторную классификацию после записи, а не пересказ намерения; записи одного
объекта идут одной транзакцией объектной модели, файл `.mdo` сбрасывается принудительно.

`check_release_fitness` отвечает, что новая поставка
ломает в расширении: заимствованный объект исчез, заимствованный реквизит исчез, сменился тип
реквизита. `list_interceptors` с `baseProjectName` дополняет это сверкой подписей обработчиков с
целевыми методами по модели BSL и разделяет то, что ломает связывание, и то, что не ломает. Он же
сверяет текст контролируемого фрагмента у `&ИзменениеИКонтроль` с телом метода поставки и называет
первую строку, которой в поставке нет, как ее написал автор; отдельно различается случай, когда все
строки на месте, но уже не единым куском. **Без `baseProjectName` не сверяется ничего**, и ответ
говорит это прямо: `validated` равно `false` и `validationNote` называет довод, который включает
проверку. Список перехватчиков, к которым нет замечаний, иначе читался бы как список перехватчиков
без замечаний. С названным базовым проектом сводка несет три счетчика - `unresolvedTargets`,
`driftedControlled` и `controlledUnchecked`, - потому что находка внутри сотой записи списка не
дошла ни до кого; последний счетчик отделяет фрагмент, который не удалось прочитать с обеих сторон
(в том числе когда базовый модуль по этому пути не найден), от фрагмента, который совпал.
**Отсутствие находок не означает, что расширение применится** - это говорит только платформа при
загрузке. Ровно ее и спрашивает `check_platform_verdict`: принимает поставку файлом `.cf` и
расширение файлом `.cfe`, создает под прогон временную информационную базу, грузит в нее сперва
поставку, затем расширение, и возвращает ответ платформы ее собственными словами. Рабочая
информационная база не открывается и блокировку не отдает, временная удаляется после прогона (а если
удалить не удалось - ответ называет ее имя). Поле `applies` несет только состоявшийся прогон и
означает ответ платформы; несостоявшийся прогон поля не имеет и называет причину в `error`; классифицированный отказ
дополнительно несет `failureKind`.

`list_extension` и `list_interceptors` на долгом обходе отвечают `Pending` с `runKey`: вызов через фасад и
прямой вызов с теми же доводами дают один `runKey`, а повторный вызов, пока прежний прогон останавливается,
отвечает `stillStopping`.
</details>

</details>

<a id="external_object_workshop"></a>
<details>
<summary><code>external_object_workshop</code> - внешние отчеты и обработки</summary>

Создает исходную структуру внешнего отчета или обработки и возвращает созданные артефакты
проекта. Обе операции (`create`, `import_external_object`) пишут рабочую область и гасятся
пресетами Read-only, Debug & Test и Code Review дверью `external_object_workshop_writes` - до
чтения рабочей области; работает `help`.

`import_external_object` добавляет `.epf` / `.erf` в существующий контейнер (`targetProjectName`, `inputPath`). Бинарник преобразуется через Конфигуратор базы проекта `baseProjectName` (по умолчанию - родительской конфигурации контейнера); `applicationId` называет приложение, когда их несколько (см. `get_applications`). Перед запуском EDT отпускает базу и берет ее обратно после: отказ отпустить - отказ импорта (`infobaseNotReleased`), отказ вернуть - поле `reconnectError` в ответе, при двойной ошибке видны обе. Ответ несет `hostProject` и `infobaseName`.
</details>

## Пресеты и видимость

| Пресет | Что видит и может вызывать агент |
|---|---|
| **Canonical** | Фасады перечислены в `tools/list`; покрываемые ими standalone-инструменты скрыты, но остаются вызываемыми. |
| **All Tools** | Показывает весь зарегистрированный набор. |
| **Read-only** | Отключает запись, отладку, запуск и обновление ИБ. |
| **Editing** | Разрешает чтение и изменение, но отключает группу отладки. |
| **Debug & Test** | Разрешает чтение, запуск, отладку и тесты; отключает изменения и опасные операции. |
| **Code Review** | Оставляет чтение и анализ BSL без записи и запуска. |
| **Custom** | Использует вручную выбранные состояния инструментов. |

Состояния отдельного инструмента:

- **listed** - отображается в `tools/list` и вызывается;
- **callable-hidden** - скрыт из списка, но прямой вызов разрешен;
- **disabled** - вызов отклоняется сервером.
