# Agent workflow reliability: design and implementation plan

Date: 2026-11-13
Status: proposed; independent plan review and Lead acceptance required before implementation.

## Purpose and boundaries

Make the twelve reported agent-workflow failures predictable and safe against the current candidate, not the historical release on which the reports originated. This is five bounded subprojects: managed forms (1, 6), MXL (3, 10, 11), client selection (2), Vanessa (4, 7, 8, 9), and extension creation (5, 12). No broad infrastructure audit, generic job-framework rewrite, automatic dependency adoption, or unrelated refactoring is included.

Source inspection was performed at candidate `daf6caab`. Existing uncommitted changelog restructuring must survive unchanged except for deliberate, Lead-owned additions. The reported 7,100 passing tests and installed runtime are supplied context, not fresh verification by this plan. No build, installation, EDT action, infobase action, commit, or release has been performed for this document.

## Alternatives and recommendation

1. **Recommended: strict preflight and explicit lifecycle outcomes.** Validate the requested placement and data path before any durable mutation; refuse unsupported extension bindings without borrowing dependencies; serialize template writes at the actual model/file boundary; expose bounded waiting, progress and cancellation truthfully. This deliberately trades some convenience for reproducible recovery.
2. **Automatic adoption and repair.** Infer a parent, borrow the root form attribute, then recursively adopt referenced metadata until export works. Reject for this sprint: dependency expansion is difficult to bound, can alter unrelated metadata, and a successful EDT check does not establish platform export validity.
3. **Documentation-only workarounds.** Tell agents to serialize everything and always pass launch flags. Retain useful guidance, but reject as the main solution: it cannot prevent lost acknowledged writes, incomplete creation, or unsafe adoption.

## Safety contracts

### Managed forms

Both preview and write execute identical structural/path preflight. An invalid `beforeName` is a refusal, not success with changed placement. A request through an inherited form root must not silently broaden extension metadata. All checks needed to establish safety must either pass or refuse with the unavailable check named. Existing own-attribute creation in one transaction remains supported when its typed local model is sufficient; do not demand derived data that cannot yet exist. The write transaction must roll back the field, path and any intermediate change on refusal. Removing a form attribute must not delete unrelated, preexisting borrowed children. Repair of already-corrupt projects is explicitly out of scope.

### MXL

Use the canonical resolved owner identity, not caller spelling, for a critical section shared by template creation, reads and content mutations: export writes the owning metadata container, so sibling templates share the persistence boundary. Different owners may proceed independently. Check readiness before identity resolution. Revalidate the expected template identity (or expected absence for creation) inside the mutation transaction before any change; a changed identity produces a typed not-started refusal, not an automatic replay. Acquire it before reading the state that informs the mutation; release it in finally after persistence/export acknowledgement. Waiting must be bounded and cancellation-aware and must not hold an EDT UI lock while awaiting derived data. Never automatically retry once the action began, committed, or its outcome is unknown. A readiness refusal identifies that nothing started. If a model/file split cannot be safely rolled back with the existing transaction/persistence mechanism, refuse before modifying either; do not hide that limitation behind success. Do not add broad BSL-to-template static analysis in this sprint. An empty-template observation may be informational, not an unconditional export error because empty templates can be intentional.

### Asynchronous lifecycle

Use existing `PendingWorkRegistry`/`PendingExecutor`, with operation-scoped keys, parameter binding, ownership and a single final result. Validate before scheduling. Polling collects the same operation and never starts a new write. Completion, exception, cancellation, expiry and interrupted waits must all release worker/process references and operation locks. A live process cannot become an untracked background job: retain ownership while it remains alive and report stop failure truthfully. Cancellation before start prevents mutation; cancellation after start reports whether completion or residual work remains. Authentication errors are actionable terminal/blocked observations, not endless generic building retries. Mask credentials and sensitive native text.

Vanessa startup timeout and scenario execution timeout are separate concepts. A startup observation deadline may return Pending without terminating the owned client. That does not remove the final bounded execution/ownership policy. Use cooperative stop for new behavior where supported; do not turn this sprint into a process-control rewrite. Existing forced-stop paths must never be exercised against user processes during acceptance. No test may operate on an arbitrary existing client, project or infobase.

## P4 followup: owned client observation lifecycle (review gate)

### Bounded implementation and ownership

- Introduce one Vanessa-local owned-run coordinator, not a shared job framework. Route synchronous and asynchronous starts through the existing `PendingWorkRegistry.VANESSA` domain; short synchronous runs still return their final result. Preserve unique per-call keys and one-run admission. Validate before preparing files or launching. A preparation entry starts at most one client.
- Separate preparation, process observation and finalization. Preparation acquires `THE_CLIENT`, `MonopolyLock.Claim` and `InfobaseAddress.Hold`, writes the run-owned files, and starts the process. Transfer all three leases and temporary-file cleanup obligations into the owned-run object before returning from preparation; remove the current stack-scoped close/finally cleanup only as part of that atomic handoff. Failure before handoff closes every acquired resource exactly once. Do not transfer a thread-affine lease: inspect these exact resource implementations first; if ownership cannot safely move, stop this approach before code rather than releasing a live client's infobase.
- Each caller waits only a bounded observation budget. A soft deadline returns `Pending` and the same `runKey`; it never kills the process or reconnects EDT while that process may hold the infobase. Both launch modes use the owned object, so a synchronous observation timeout cannot create an untracked process. Keep owned scenario/settings files until the process and its owned descendants have exited, then remove sensitive input files using existing cleanup behavior; retain report/screenshot output as before.
- The coordinator has capacity one. It holds the exact `Process` and descendant handles/start identities captured from that process, never discovers targets by name. Refresh descendant ownership on every observation while the parent exists, retaining previously captured handles after parent exit; a late-spawned descendant is not forgotten when the parent exits. Polling observes that same run and never launches again. Explicit cancellation is the only path that requests process stop in this conversion. `timeoutSeconds` becomes an observation deadline, not a hard kill deadline; there is no second implicit hard-stop timer. An indefinitely alive client remains owned and blocks new admission until explicit cancellation or confirmed exit. This deliberate policy change must be documented; do not preserve the old timeout kill under another name. Failed or uncertain stop retains the key, leases and admission slot, with a truthful residual-work answer.
- Do not occupy an executor thread for the client's whole lifetime. Use one Vanessa-local single-thread `ScheduledThreadPoolExecutor`, bounded structurally to one periodic observation registration and at most one finalizer for the capacity-one run; canceled tasks are removed. Each observation checks liveness/owned windows within its existing native-reader budget and returns; overlapping poll/exit/cancel observations coalesce rather than enqueue. No per-poll thread creation, unbounded task queue, recursive resubmission or long sleeping worker. Process-exit notification requests an observation rather than finalizing by itself, because descendants may remain alive. A single atomic transition claims finalization after confirmed exit of all captured owned processes; parsing, resource release and final-result publication run once. `InfobaseAddress.Hold`, the monopoly claim and semaphore are closed/released by that one finalizer only after ownership transfer; failure-before-transfer uses a separate atomic acquisition cleanup owner. An unavailable liveness query means ownership is unresolved, not that the process exited.

### Exact registry and expiry boundary

`PendingWorkRegistry.VANESSA` currently has one worker and a 70-minute abandoned TTL. Its current abandoned-entry logic skips work that began, but completed entries still expire. Preparation returning is not run completion. The Vanessa-local owned map must therefore be authoritative before registry lookup/removal/pruning: active or stopping runs remain addressable under the original key and block admission even if the preparation future or its cached response expires. Do not refresh TTL to disguise completion, create a second registry domain, or drop an alive process to satisfy a timer.

Use existing registry work only for bounded preparation/finalization, with the owned object representing the operation between tasks. `ToolRoad.isOwnPoll` currently requires an unfinished registry entry; resolving only inside Vanessa is therefore insufficient. Lead owns the narrowly scoped integration: `PendingWorkRegistry` accepts a domain-local live-owned-key predicate, and `ToolRoad` consults `domain.isOwnedLivePoll` only after validating the registered tool/domain/operation and existing request/project scope binding. `VANESSA` binds that predicate to its exact owned-run map, including stopping and finalizing states; false is the default for all other domains and unknown/collected keys. Do not grant arbitrary run-key, operation, project or tool bypass. Tests must show an authentic owned Vanessa poll passes the same scope gates after preparation completes and after preparation-cache expiry, while a foreign operation/project/key cannot gain that exemption. The predicate keeps reachability, not a second result cache; it does not make completed preparation an unfinished worker.

Poll first resolves the scoped owned object; final collection atomically returns the final answer and removes it, retaining the existing single-collection contract. The one periodic observer notices exit even when nobody polls and performs cleanup; completed-but-uncollected local answers expire after the existing completed-result retention duration, not indefinitely. An alive abandoned process remains owned and admission-blocking with an explicit cancel instruction: expiry must not silently kill it or forget its leases. Lead also owns one explicit Activator shutdown hook for the local scheduler: cancel observation registrations, stop accepting submissions and call bounded executor shutdown without killing the owned client; report any still-owned process/leases as unresolved rather than claiming cleanup. Plugin shutdown cannot guarantee continued process tracking after the host exits, which must be a stated limitation, not a successful release. Before implementation, Lead must accept these exact shared-file changes. If that hook, scope-bound poll exemption, single resource closer or structurally bounded scheduling requires a broader framework rewrite, stop the followup at this gate instead of growing it.
